This file is the worked example. Delete it along with the example rows in
`MERGE_PLAN.md` on day one.

**The filename is derived from the row ID, not written down anywhere.** Row `1` →
`tasks/MP-001.md`. Zero-pad to three digits so the folder still sorts in ID order
once you pass task 99. There is no pointer column in the summary table on purpose:
a pointer can be typo'd, a convention cannot.

**Write this document so a stranger can execute it.** Another agent, or an
unattended scheduled run, must be able to pick the task up cold — no "continue
what we discussed," no unstated context. Name the files, state the acceptance
criteria, and give the *why* inline.

**Write it as long as the work honestly needs.** That is the whole point of the
split: this file is not in the boot path, so depth costs nothing per session. The
summary-table row costs ~50 tokens and is the only part every session pays for.

What belongs here:

- What needs to happen, and what "done" looks like.
- The reasoning — including approaches considered and rejected, and why. This is
  the part that is worth the most in six months and the part a commit message
  never captures.
- Files, paths, commands, gotchas. Anything that would otherwise be re-derived.
- If the row is blocked: *why* it is blocked and what the upstream task must
  produce first. The bare fact "blocked by 3" belongs in the table's Blocked-by
  column, not here.

What does NOT belong here:

- Status, owner, or blocked-by IDs. The table owns state. If this document also
  claims a status, the two can disagree and neither will announce it.
- Session narrative. That goes in the journal block in `MERGE_PLAN.md`.

**When the task closes,** flip the row to ✅ or ❌ and move this file to
`tasks/closed/`. `scripts/rotate.py` does the move for you at close. There is no
waiting period — the file was never in the boot path, so there is nothing to age
out. It stays greppable in `tasks/closed/` forever.
