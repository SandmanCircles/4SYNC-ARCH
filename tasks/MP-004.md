## Why this is blocked

**The bare fact lives in the table, not here.** Row 4's `Blocked by` cell says `#2`, and
that is the single source of truth for the relationship — if this document also declared
it, the two could disagree and neither would announce it.

What belongs here is the part a cell cannot hold: *why*. This backfill has no stable key
to write against until row 2 lands a transaction ID on every settled payment. Run it
before then and it either invents keys it cannot reconcile later, or silently skips the
rows it cannot match — and the second failure is invisible until someone audits.

## What the upstream task must produce

- a transaction ID present on every settled payment, not just new ones
- stable across retries, so a replayed webhook does not mint a second identity
- exposed wherever this task will read from, not only in the provider's dashboard

**If you cannot write this list, the dependency is not understood yet** — and that is
worth discovering now rather than on the day row 2 closes and this one turns out to
still be blocked on something nobody named.

## Unblocking it

have delivered something *close* to the list above rather than the list itself — a
different field name, or an ID that turns out not to survive retries. Check, then move
the row. **A blocked task that unblocks itself by assumption is how a stale dependency
ships.**
